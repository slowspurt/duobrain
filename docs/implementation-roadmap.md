# duobrain 구현 우선순위 제안

상태: 구현 전 우선순위 검토안. 제품 범위는 [기획서](../README.md)에 정의되어 있으며, 아래 단계는 기능 제외가 아닌 구현 순서를 제안한다.

## 현재 위치와 첫 목표

현재 저장소에는 제품 기획서가 있고 실행 가능한 구현은 없다. 첫 목표는 두 개의 독립 클론에서 한 사람이 요청한 정보를 상대 AI가 보충하고, 요청한 사람과 대시보드가 그 결과를 확인하는 것이다.

화면에 표시할 기록의 형식과 전달 방식을 먼저 정한다. 프롬프트·하네스의 당시 버전과 시간 기록도 초기에 수집해야 뒤에서 비교·분석할 수 있다. 동시 작업 지원이 검증되기 전 첫 시연은 순차적으로 작업한다.

## 단계별 순서

| 순서 | 작업 | 먼저 필요한 이유 | 완료 기준 |
| --- | --- | --- | --- |
| 0 | 공유 기록과 동기화 규약 | 모든 AI 동작과 화면이 같은 의미의 기록을 읽어야 한다. | 참여자 2명, 목표·계획·작업 구간·티켓·근거·지식 상태의 예시와 상태 전이, 공유할 브랜치 구조를 문서화한다. |
| 1 | Git 기반 핵심 동작 | 기록 전달이 실패하면 대시보드와 AI가 잘못된 상태를 믿게 된다. | 시작·마무리 기록, 티켓 생성·응답·해결·재오픈, 동기화를 두 클론에서 재현한다. 푸시 실패와 동시 쓰기 후 재시도에서 기록이 유실·중복되지 않는다. |
| 2 | 최초 AI 연결과 기획 점검 | 사용자가 매번 CLI 사용법과 협업 절차를 설명하지 않아야 한다. | 우선 하나의 AI 도구로 초기 기획 점검, 회의록 반영, 시작 브리핑, 티켓 처리, 인계와 마무리를 수행한다. 두 번째 참여자는 기존 계획을 이어받는다. |
| 3 | 실제 기록을 읽는 대시보드 | 사용자가 AI의 처리와 미해결 사항을 직접 확인할 수 있어야 한다. | 전체·중기·현단계 목표, 두 사람의 범위, 최근 작업 구간, 기록된 병목, 요청함·진행 중·처리 이력·티켓 상세와 동기화 상태를 제공한다. |
| 4 | 동시 작업과 워크트리 | 실제 두 사람이 같은 시간에 사용하는 데 필요한 단계다. | 나중에 시작한 AI의 워크트리 분리, 상대 변경 확인, 작업 중 범위 갱신과 추적을 검증한다. 거의 동시 시작·오래된 상태·미푸시 변경·통합 충돌을 구분한다. |
| 5 | 작업 방식 비교와 결정 근거 탐색 | 앞 단계에서 확보한 실제 기록을 활용한다. | 동일 작업의 프롬프트·하네스 차이를 당시 버전으로 설명하고, 부족하면 티켓으로 보충해 답변을 이어간다. 결과물에서 결정 근거와 인계 기록으로 이동할 수 있다. |
| 6 | 시간 사용과 병목 분석 확장 | 수집한 기록의 정확성과 누락 상태를 이해한 다음 분석해야 한다. | 작업별 시간 사용, 최근 기간 집계, 많이 소요된 부분과 병목 후보를 제공한다. 경과 시간·실제 기록 시간·추정·대기를 구분하고 중복 집계를 방지한다. |
| 7 | 하루 1회 위키 정제와 배포 준비 | 실제 기록과 사용 흐름이 있어야 무엇을 보존·요약할지 검증할 수 있다. | 출처·공동 합의·미해결 티켓을 보존하며 중요도·최신성을 재평가한다. 예약 실행, 중복 실행 방지, 실패 복구와 변경 이력을 검증하고 새 환경에서 설치·클론·시작을 확인한다. |

## 0단계에서 닫아야 할 설계 문제

- 코드 병합 전에도 두 사람이 시작·마무리 기록과 티켓을 읽는 방법. 우선 같은 원격 저장소의 협업 기록 전용 브랜치를 후보로 검토한다. 이는 아직 확정된 구조가 아니다.
- 양쪽에서 같은 티켓이나 위키를 수정할 때의 충돌 처리. 고유 ID의 개별 이벤트 기록과 여기서 계산한 상태를 후보로 검토한다. 매번 공용 파일 하나를 덮어쓰는 구조는 피하는 방향으로 검증한다.
- 공유된 기록과 로컬에만 있는 기록의 구분. 커밋 성공, 푸시 성공, 상대의 확인, 실제 해결을 별개의 사실로 기록한다.
- 사람의 응답이 필요한 피드백과 AI가 처리할 수 있는 정보 보충의 완료 조건.
- 두 참여자의 식별, 설정 범위, 사용할 첫 AI 연결 방식. 다인용 권한 구조는 만들지 않는다.
- 문서와 이벤트의 버전, 출처, 작성 주체, 작업 당시 프롬프트·하네스 식별 방법. 상세 비교 화면은 나중이어도 근거는 처음부터 남긴다.

문서는 사람이 읽을 수 있는 형태를 유지하고, 상태를 변경하는 핵심 동작에는 공통 검증을 둔다. 구체적인 언어·프레임워크·스키마는 이 검토만으로 확정하지 않는다.

## 처음부터 수집하고, 나중에 분석할 정보

1~2단계에서 시작·종료·일시정지·재개, 작업 범위와 목표, 기록된 병목, 출처와 커밋, 프롬프트·하네스의 사용 버전 또는 보존 가능한 참조를 남긴다. 수집하지 못한 항목은 미확인으로 기록한다.

3단계 대시보드에는 이 실제 기록을 먼저 보여준다. 작업별 시간 추정, 병목 자동 탐지, 고급 비교는 5~6단계에서 확장한다. 이 순서로 초기 화면을 실제 협업에 사용하면서 분석에 필요한 데이터도 쌓는다.

## 첫 시연의 완료 기준

3단계까지 완료하면 다음 순차 협업 흐름을 시연한다.

1. A가 기획서 또는 회의록으로 협업 기획을 정리하고 B가 다른 클론에서 이를 확인한다.
2. A가 시작 기록을 공유하고, B의 작업 방식에 대한 정보 보충 티켓을 남긴 뒤 마무리한다.
3. B의 AI가 시작 시 티켓을 읽고 허용 범위의 기록을 위키에 보충해 공유한다.
4. A의 AI가 보충된 근거를 확인해 답변하고, 대시보드의 진행 중 티켓이 처리 이력으로 전환된다.
5. 사람에게 직접 요청한 피드백은 B의 AI 응답만으로 해결되지 않는다.
6. 완료된 티켓의 상세와 근거를 다시 찾아볼 수 있다.

두 로컬 클론을 이용한 자동 검증 후 실제 두 환경에서 확인한다. 4단계를 통과하면 동시 작업 사용을 검증하고, 전체 제품 범위의 완료는 7단계까지 확인한다.

## 검증에 집중할 부분

공유 실패·재시도, 같은 티켓에 대한 동시 변경, 잘못된 상태 전이, 사람 피드백의 조기 종료, 미종료 작업 시간의 과대 집계, 위키 정제 중 출처·합의 상태·미해결 요청 손실을 검증한다. 화면은 실제 기록으로 요청 생성부터 이력 조회까지 확인한다.

다음 구현 작업의 구체적인 산출물은 0단계의 최소 데이터 예시, 상태 전이 규칙, 두 클론의 동기화 설계다.
